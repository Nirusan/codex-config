# Working agreements

- Respond in French. Use English for code, commits, technical documentation, and configuration; preserve the product's language.
- Use repository-pinned pnpm. Follow existing conventions; use descriptive names, functional code, and the configured import alias. Keep TypeScript strict, avoid `any`, type public boundaries, and validate external data. Prefer type-only imports and exhaustive union handling. For new TypeScript projects, prefer `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`; avoid broad unrelated migrations.
- Start with relevant current instructions, source, and specifications. Retrieve history when requested or to resolve a specific uncertainty; search exact identifiers and bounded excerpts before broadening. Follow the project's source-of-truth hierarchy. Do not reload available context; batch independent reads and checks when practical.
- Complete authorized local work and its required checks. Clarify material ambiguity; reuse authorization within its stated scope. An audit remains read-only. Do not commit unless the user requests a commit. Publication, production writes, destructive actions, new recurring costs, and material product/privacy changes need authorization for that effect.
- Preserve unrelated work and the repository's ownership and isolation rules.
- Verify changed behavior and required repository gates. Reuse evidence for the same revision and environment; repeat checks when edits or unresolved failures justify it. Distinguish source, tests, publication, installation, and actual user behavior in claims.
- Update documentation when the requested change makes it inaccurate or leaves a necessary contract undocumented. A repair that restores an already documented rule needs no documentation rewrite. Update an existing task tracker when applicable; avoid duplicate progress narratives.
- Use existing design, components, assets, copy, and states. Do not invent product facts. Use appropriate browser or native checks for visual changes; Gemini design tooling is opt-in.
- Load a skill for its relevant specialized knowledge or tool procedure. Routine edits, verification, and documentation can be completed directly. Explicitly requested skills and applicable project-specific procedures still apply.
